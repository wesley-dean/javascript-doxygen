# ADR-025: Build JavaScript distribution artifacts

Date: 2026-09-14

## Status

Accepted

## Context

ADR-012 deliberately deferred the Python-specific distribution and release
interfaces copied into this repository while `javascript-doxygen` established its
own JavaScript behavior and integration contracts.  The maintained filter is now
stable enough to establish a JavaScript-specific build boundary.

Consumers of the sibling `awk-doxygen`, `bash-doxygen`, and `python-doxygen`
projects use the same basic model: a project pins one released filter through
`bashdeps`, materializes that one executable filter beneath its local `vendor/`
directory, and configures its own Doxyfile to apply the vendored filter to the
corresponding source-file patterns.

`javascript-doxygen` must preserve that model.  A consumer is expected to pin one
released AWK filter, for example:

```text
vendor/javascript-doxygen.awk
```

and configure its Doxyfile so `*.js` files are processed through that filter.
Alias-backed JavaScript representations also require Doxygen `ALIASES`
definitions.  Those definitions belong to the consumer-owned Doxyfile contract;
they do not turn the repository's checked-in `doxygen-javascript.conf` reference
fragment into a second runtime dependency.

The repository also needs inspectable generated forms for development, ordinary
distribution, and minified distribution.  The existing `awk-minifier` project
already establishes a conservative model for producing three AWK artifacts and
adjacent SHA-256 checksum files while using a pinned previous AWK Minifier release
as the production minification trust root.

Issue #17 requests the same three-artifact build surface for this repository:

```text
dist/javascript-doxygen.dev.awk
dist/javascript-doxygen.awk
dist/javascript-doxygen.min.awk
```

with an adjacent `.sha256` file for each artifact.

## Decision Drivers

- Preserve the established one-file downstream runtime dependency model.
- Keep maintained source distinct from generated consumer artifacts.
- Make generated bytes inspectable and reproducible from reviewed source.
- Keep ordinary and minified artifacts semantically equivalent to maintained
  source.
- Use a reviewed, pinned AWK Minifier release rather than candidate
  self-minification.
- Keep steady-state builds offline after repository dependencies are prepared.
- Make every generated artifact independently verifiable with SHA-256.
- Do not silently re-enable copied Python release automation before a separate
  JavaScript release-publication decision is accepted.

## Decision

### Maintained source

The maintained filter remains:

```text
doxygen-javascript.awk
```

Generated `dist/` content is derivative build state and SHALL remain ignored by
Git.

### Build artifacts

`make build` SHALL produce exactly these executable AWK artifacts:

```text
dist/javascript-doxygen.dev.awk
dist/javascript-doxygen.awk
dist/javascript-doxygen.min.awk
```

The development artifact SHALL contain the complete documented maintained filter
plus generated comment-only provenance.

The ordinary artifact SHALL be derived from the development artifact and SHALL
remove only project-governed AWK Doxygen documentation records beginning with
`##`.  It SHALL preserve ordinary implementation comments and executable behavior.

The minified artifact SHALL be derived from the ordinary artifact body using the
pinned released AWK Minifier declared in `dependencies.txt`.  Generated provenance
SHALL remain outside the minifier input and SHALL be regenerated for the minified
artifact so the artifact identifies its source version, build commit, build date,
and minifier version.

The current candidate SHALL NOT be used as its own production minifier.  Missing,
unverified, or failed minifier state is a build failure rather than permission to
copy another artifact or fall back to self-minification.

### Checksums

The build SHALL create one adjacent checksum file for every generated AWK artifact:

```text
dist/javascript-doxygen.dev.awk.sha256
dist/javascript-doxygen.awk.sha256
dist/javascript-doxygen.min.awk.sha256
```

Each checksum file SHALL use the ordinary `sha256sum`-compatible form:

```text
<64 lowercase hexadecimal characters>  <artifact basename>
```

The repository SHALL provide an offline verification target that validates all
three checksum files against their corresponding artifact bytes.

### Dependency preparation

`awk-minifier` SHALL be a pinned build dependency synchronized by `bashdeps` from
an immutable release URL and committed SHA-256 digest.  Build dependencies SHALL
be declared in `dependencies.txt`.

Documentation-only dependencies SHALL remain in `dependencies-docs.txt`.
Multiple manifests may share `vendor/` because `bashdeps sync` does not prune
files that are absent from the current manifest.

`make deps` MAY access the network and SHALL converge build dependency state.
`make deps-check` SHALL verify prepared build dependency state without repair.
`make build` SHALL remain network-free and SHALL fail when required prepared
build state is absent or invalid.

`make all` SHALL be the convenience lifecycle that prepares build dependencies
and then produces the six requested `dist/` outputs.

### Test parity

The existing TAP regression suite SHALL continue to exercise maintained source.
The generated development, ordinary, and minified artifacts SHALL each run through
the same regression suite.  Their adjacent checksums SHALL also be verified.

The JavaScript/Doxygen integration surface SHOULD also exercise generated
artifacts so alias-backed and Doxygen-facing behavior is proven against the same
bytes that could later become release candidates.

### Consumer contract

This decision preserves a one-file runtime dependency contract.

A downstream consumer using `bashdeps` SHALL materialize one released executable
AWK filter, conventionally:

```text
vendor/javascript-doxygen.awk
```

The consumer owns its Doxyfile.  That Doxyfile SHALL map JavaScript files to the
JavaScript parser and apply the vendored filter, conceptually:

```text
EXTENSION_MAPPING = js=JavaScript
FILTER_PATTERNS   = *.js="awk -f vendor/javascript-doxygen.awk --"
```

The consumer Doxyfile SHALL also define the governed JavaScript aliases required
by supported alias-backed representations.  The repository README SHALL document
the exact current alias block.

`doxygen-javascript.conf` remains a repository reference and integration-test
fixture for those definitions.  It is not a second runtime dependency, is not a
file consumers are required to fetch with `bashdeps`, and is not part of the
one-file filter dependency contract.

This decision supersedes ADR-019 only where ADR-019 suggested that consumers copy
or include `doxygen-javascript.conf` from the repository revision.  ADR-019's
alias-backed yields representation and line-preservation decision remain accepted.
The same clarification applies to later ADRs that use the checked-in configuration
fragment as integration evidence: consumers reproduce the governed alias
configuration in their own Doxyfile rather than acquiring the fragment as another
runtime artifact.

### Release publication remains separate

This ADR establishes local deterministic build artifacts and build evidence.  It
does not enable semantic-version release publication, choose which generated form
will become the released runtime filter, or reactivate copied Python release
workflows.

A later JavaScript-specific release ADR SHALL preserve the one-file runtime
consumer model established here.  SHA-256 data may be published as verification
metadata, but downstream execution SHALL depend on one AWK filter file.

## Alternatives Considered

### Release `doxygen-javascript.conf` as a second consumer dependency

Rejected.  The established sibling workflow gives a consumer one vendored filter
and leaves Doxyfile configuration in the consuming repository.  A second runtime
file would complicate `bashdeps` consumption and weaken the intended one-file
filter interface.

### Embed Doxyfile aliases into the AWK artifact

Rejected because Doxygen aliases are parser configuration, not AWK executable
behavior.  The input filter cannot reliably configure the consumer's Doxygen
process, and mixing those concerns would make the artifact interface misleading.

### Publish only the maintained source file

Rejected for the build boundary because explicit generated artifacts provide
provenance, allow documentation stripping and minification to be tested, and make
future release candidates inspectable before publication.

### Use the candidate minifier to minify itself

Rejected as a production trust model.  Production minification must use a pinned,
previously released AWK Minifier artifact supplied through `bashdeps`.

### Download the minifier directly from the Makefile

Rejected.  Repository dependency acquisition belongs to `bashdeps`; build recipes
consume prepared, verified state and remain network-free.

### Re-enable release publication in the same increment

Rejected because artifact construction and release publication are distinct
contracts.  The repository should first prove deterministic generated artifacts,
checksum verification, and semantic parity before publishing versioned consumer
bytes.

## Consequences

Developers gain one canonical build lifecycle that produces development,
ordinary, and minified forms plus independent hashes.

The build acquires an explicit dependency-preparation step for AWK Minifier.
Ordinary `make build` becomes an offline operation over already prepared state,
while `make all` may synchronize the pinned dependency before building.

Generated artifact regressions become visible before release publication exists.
A transformation that changes filter semantics, loses provenance, or produces an
invalid checksum fails the repository test surface rather than becoming a latent
consumer problem.

Consumers continue to fetch one runtime filter file through `bashdeps`.  They must
also configure their Doxyfile correctly, including the documented aliases, just as
they already configure the appropriate file pattern and filter path.

Release publication remains deferred and requires its own accepted JavaScript
contract.

## Expected Outcomes

After build dependencies are prepared:

```text
make build
```

creates all six requested `dist/` files without network access.

From an unprepared checkout:

```text
make all
```

prepares the pinned AWK Minifier dependency and then creates the same six files.

The regression suite passes against maintained source and all three generated AWK
artifacts, and checksum verification succeeds for all three corresponding hashes.

A future consuming repository can pin one released `javascript-doxygen.awk` with
`bashdeps`, materialize it beneath `vendor/`, and configure its own Doxyfile to use
that file for `*.js` input together with the documented alias definitions.

## Compatibility and Migration

No current released JavaScript consumer artifact exists, so this build contract
does not break an established release interface.

The existing maintained-source and Doxygen integration behavior remain unchanged.
The only consumer-facing clarification is that the alias definitions are Doxyfile
configuration requirements, while `doxygen-javascript.conf` itself is not a
runtime dependency.

Future changes to artifact names, ordinary-artifact stripping policy, minifier
lineage, checksum format, the one-file consumer model, or required Doxyfile alias
semantics are compatibility decisions and require ADR review.
